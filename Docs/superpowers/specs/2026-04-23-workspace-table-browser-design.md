# C# 配置表查看器第一阶段设计

日期：2026-04-23
状态：已确认，待进入实施计划
范围：第一阶段只做工作区浏览和只读表格查看，不做源码编辑器，不做 DLL 语义接入

## 1. 背景与目标

当前项目的方向是做一个适合 C# 强类型配置数据的表格工具，长期目标是达到接近 Excel 的高效体验，但不照搬 Excel，而是围绕 C# 配置、枚举、注释、实例初始化器这些场景做专门优化。

本次设计只覆盖第一阶段，目标收敛为：

- 软件可手动打开任意目录。
- 支持通过命令行参数传入目录，便于 VS Code task 一键启动测试。
- 左侧显示类似 VS Code 的工作区目录树。
- 目录树只显示文件夹和 `.cs` 文件。
- 点击某个 `.cs` 文件后，右侧只显示表格视图，不显示源码。
- 如果文件可解析成配置表，则展示表格。
- 如果文件当前不可解析，则展示只读提示态，不切换到代码编辑模式。
- 缓存最近打开目录，便于重复进入工作区。

## 2. 非目标

第一阶段明确不做以下内容：

- 不做文本代码编辑器。
- 不显示原始 C# 代码。
- 不做 DLL 加载作为启动前提。
- 不把 Godot 运行时或游戏工程依赖接入工具运行链路。
- 不做保存回写。
- 不做完整强类型语义校验。
- 不把工具演化成通用 IDE。
- 不把任意 C# 代码都尝试转换成表格。

这些内容保留给后续阶段。

## 2.1 可表格化规则

“哪些 `.cs` 能转换成表格”已经单独定为硬规则，见：

- `Docs/CSharp强类型配置可表格化规则.md`

第一阶段按其中的 Phase 1 边界执行：

- 单个 `.cs` 文件中只能有一个主配置 class。
- 主配置 class 必须有可作为列的 public 实例属性。
- 文件必须有可作为行的 `public static readonly` 静态实例。
- 静态实例必须使用 `new()` 或 `new Type()` 对象初始化器。
- `<summary>` 用于属性说明和实例说明。
- 不满足规则时显示诊断视图，不进入源码编辑或任意代码解释。

Schema 文件、enum 文件、普通行为代码文件都不是数据表文件。它们可以在后续阶段参与继承、枚举下拉和类型索引，但第一阶段不把它们打开成空表。

完整表格编辑器的长期产品规格见：

- `Docs/面向CSharp强类型配置的表格编辑器完善计划.md`

该计划覆盖工作区隐藏、表格布局统一、设置面板、筛选排序、批量编辑、类型化编辑和保存回写。本文档仍只描述第一阶段工作区表格浏览，但第一阶段实现不能和长期规格冲突。

## 3. 当前代码库实际状态

当前仓库已经有一个 `WinForms + ReoGrid + 纯源码解析` 的原型，主要代码集中在：

- `Src/MainForm.cs`
- `Src/Core/ConfigTypeScanner.cs`
- `Src/Parsing/SourceParser.cs`
- `Src/Parsing/CsCommentParser.cs`
- `Src/UI/SheetBuilder.cs`

现有实现与旧文档之间存在偏差：

- 现有代码已经不是“先加载 DLL 再反射”的方案。
- 当前主路径是“直接扫描目录中的 `.cs` 文件，再用正则/源码解析构建表格”。
- `MainForm` 当前是“打开一个数据目录，左侧列类型列表，右侧显示表格”。
- 这与本次确认的“左侧工作区目录树，点击具体 `.cs` 文件打开表格”仍有明显差异。

## 4. 已验证的关键问题

本次设计前已实际执行 `dotnet build`。当前最优先的问题不是“运行时缺少 DLL 定义”，而是工具项目的编译边界错误。

已确认现象：

- `DataConfigEditor.csproj` 当前把 `Src/Data/**` 下大量 Godot 游戏源码一起编译进工具项目。
- 构建时出现大量错误，核心缺失包括 `Godot`、`ExportAttribute`、`ExportGroupAttribute`、`DataKey`、`AbilityFeatureHandlerBase` 等。
- 这说明当前第一阻塞点是“工具工程边界与被解析数据样例混在一起”，而不是先补外部 DLL。

结论：

- 第一阶段必须先把工具自身代码与被解析样例/游戏源码隔离。
- DLL、Roslyn 语义、工程引用解析不应成为第一阶段验收前提。

## 5. 方案选型

设计阶段考虑过三条路线：

### 方案 A：工作区浏览器优先

保留 `WinForms + ReoGrid + 纯源码解析`，先实现工作区目录树、最近目录、启动参数、单文件点击后表格展示。

优点：

- 与本阶段目标完全一致。
- 能最快获得一个真实可用的桌面工具。
- 可以避开 DLL、MSBuild、Godot 运行时等高复杂度前置条件。
- 为后续增强保留足够接口。

缺点：

- 解析精度受当前源码解析器能力限制。
- 复杂泛型、跨文件语义、继承链等能力需要后续补强。

### 方案 B：Roslyn 语法树优先

先把当前解析器升级到 Roslyn syntax tree，再做工作区壳子。

优点：

- 单文件结构解析会比正则更稳。
- 后续升级到语义分析更自然。

缺点：

- 第一阶段交付速度会被拖慢。
- 用户最关心的目录浏览和表格查看价值不能尽快落地。

### 方案 C：工程语义优先

直接引入 `MSBuildWorkspace + Microsoft.Build.Locator + Roslyn`，尝试加载真实项目语义和引用。

优点：

- 最接近长期的强类型工具形态。

缺点：

- 复杂度最高。
- 会立刻卷入 SDK 探测、项目加载、引用恢复、Godot 项目兼容等问题。
- 不适合作为第一阶段。

推荐结论：第一阶段采用方案 A。

## 6. 外部生态与可复用能力

### 6.1 表格控件

第一阶段继续使用 `ReoGrid` 作为表格 UI 底座。

理由：

- 现有项目已接入，迁移成本最低。
- 支持 WinForms/WPF、冻结、下拉、分组 outline、图片等能力。
- 对“目录浏览 + 只读表格查看”已经足够。

后续若需要更强 Excel 兼容性，可再评估商业方案：

- Syncfusion WinForms Spreadsheet
- MESCIUS Spread.NET

### 6.2 C# 解析与语义能力

第一阶段不强制引入 Roslyn 作为实施前提，但长期路线明确：

- 单文件结构增强优先考虑 Roslyn Syntax API。
- 工程级语义增强优先考虑 `MSBuildWorkspace`。
- 如果后续要按真实项目环境解析引用，则需要 `Microsoft.Build.Locator` 协助绑定正确的 MSBuild/SDK。

### 6.3 结论

第一阶段不做“先找 DLL 才能运行”。

正确顺序应为：

1. 工具项目可独立构建运行。
2. 工作区目录树可打开外部目录。
3. 单文件表格查看可用。
4. 再增强跨文件解析和类型系统。
5. 最后再决定是否引入 Roslyn 语义和项目级依赖解析。

## 7. 第一阶段功能设计

### 7.1 启动行为

支持两种进入方式：

- 手动点击“打开目录”。
- 启动参数传入目录路径。

启动参数优先级：

1. 如果传入路径参数，优先打开该目录。
2. 未传参数时，进入欢迎态。
3. 欢迎态展示最近目录和“打开目录”入口。

不自动打开固定测试目录。测试目录只用于 VS Code task 或命令行参数。

### 7.2 工作区目录树

左侧目录树行为：

- 显示文件夹。
- 只显示 `.cs` 文件。
- 不显示其他文件类型。
- 支持展开/折叠目录。
- 点击 `.cs` 文件时触发右侧表格加载。
- 支持默认隐藏无关目录，至少包括 `bin/`、`obj/`、`.godot/`、`.git/`、`.idea/`、`.vscode/`、`.history/`、`.superpowers/`。
- 后续通过设置面板支持用户自定义隐藏规则。

第一阶段不做：

- 多标签页
- 拖拽排序
- 文件重命名
- 新建文件

### 7.3 右侧表格区

右侧永远是表格视图区域，不提供代码视图。

允许三种显示状态：

- 可解析表格：显示列、行、注释、实例。
- 不可表格化：显示说明文本，例如“当前文件无法转换为表格视图”。
- 加载失败：显示错误态，但不影响工作区继续使用。

不可表格化原因必须具体，例如“缺少静态实例”“没有可作为列的 public 属性”“发现多个候选配置类”“静态实例不是对象初始化器”。避免只显示泛化错误。

右侧表格布局必须统一：

- 表格容器填满右侧区域。
- 表格左上角使用固定边距。
- 表头固定在顶部。
- 实例名列固定在左侧。
- 不允许不同文件因为行数少而出现表格漂在顶部小区域、滚动条位置异常等问题。
- 空表、诊断视图和加载失败视图共用同一套内容锚点。

### 7.4 最近目录

最近目录本地缓存保存：

- 最近目录列表
- 最后一次打开目录

策略：

- 不存在的路径在 UI 中标记为无效，必要时清理。
- 参数打开成功后也进入最近目录列表。

## 8. 架构设计

建议将工程整理为五层职责。

### 8.1 Workspace 层

职责：

- 打开目录
- 构建目录树
- 过滤 `.cs` 文件
- 维护最近目录
- 处理启动参数

不负责表格构建和 C# 语义判断。

### 8.2 Document 层

职责：

- 定义统一的表格文档模型

建议核心模型：

- `TableDocument`
- `TableColumn`
- `TableRow`
- `TableCell`
- `ParseDiagnostic`

该层作为 UI 和解析器之间的边界，避免 UI 直接依赖当前解析器内部结构。

### 8.3 Parser 层

职责：

- 把单个 `.cs` 文件转换成 `TableDocument`

第一阶段继续沿用纯源码解析思路，但从“目录扫描器中心”改为“单文件解析中心”。

建议拆分方向：

- `WorkspaceScanner`：列文件和目录
- `CsTableParser`：解析单文件并产出表格文档
- `SharedTypeIndex`：后续可选，用于跨文件查枚举、基类、共享定义

### 8.4 Presenter 层

职责：

- 维护当前工作区状态
- 维护当前选中文件
- 管理右侧显示状态
- 对接 UI 事件

它不是完整 MVVM，只是为了避免 `MainForm` 继续承担过多状态和业务逻辑。

### 8.5 UI 层

职责：

- WinForms 窗体
- TreeView
- ReoGrid
- 状态栏
- 工具栏

UI 只负责交互呈现，不直接承担解析拼装逻辑。

## 9. 错误处理

错误处理原则是“当前文件失败不影响整个工作区”。

第一阶段约定：

- 目录打开失败：状态栏提示，左树清空。
- 文件不存在：右侧显示文件失效提示。
- 文件不可解析：右侧显示只读提示态。
- 解析异常：记录诊断并在右侧显示简短原因。
- 不使用复杂弹窗打断主流程，除非是目录选择器这类交互本身。

## 10. 阶段拆分

### Phase 1：工作区浏览壳子

- 修复工具项目编译边界
- 支持命令行目录参数
- 支持手动打开目录
- 支持最近目录缓存
- 左侧目录树只显示文件夹和 `.cs`
- 左侧目录树支持默认隐藏无关目录
- 点击 `.cs` 后右侧显示表格或提示态
- 右侧表格布局统一，不因表格大小不同而漂移

### Phase 2：表格文档模型稳定化

- 建立 `TableDocument` 中间模型
- 调整当前解析逻辑为单文件驱动
- 稳定属性、注释、实例、分组展示

### Phase 3：工程级类型增强

- 增加跨文件枚举、基类、共享定义索引
- 评估正则增强与 Roslyn syntax 的切换点
- 明确哪些信息需要跨文件解析

### Phase 4：编辑与强类型能力

- 保存回写 `.cs`
- 针对布尔、数字、枚举做类型化单元格
- 增加校验
- 必要时再引入 Roslyn 语义或工程引用加载

## 11. VS Code 任务要求

第一阶段至少提供三个任务：

- `build`：构建工具项目
- `run`：普通启动
- `run:test-data`：启动时传入测试目录 `E:\Godot\Games\MyGames\复刻土豆兄弟\brotato-my\Data\DataNew`

## 12. 验收标准

第一阶段完成的判断标准：

- 工具项目可独立构建运行，不再因样例/Godot 代码导致构建失败。
- 软件可通过按钮打开目录。
- 软件可通过命令行参数打开目录。
- 左侧显示文件夹和 `.cs` 文件树。
- 左侧默认隐藏 `bin/`、`obj/`、`.godot/` 等无关目录。
- 点击 `.cs` 文件后，右侧只出现表格视图或提示态，不出现源码编辑器。
- 多个可解析 `.cs` 文件的表格起始位置和填充区域一致。
- 最近目录可记录并复用。

## 13. 风险与后续决策点

主要风险：

- 当前正则解析器面对复杂语法可能不稳定。
- 表格文档模型若设计过于贴合现有数据结构，后续迁移到 Roslyn 会产生重复改造。
- 如果继续把样例数据与工具源代码放在同一个编译集合，后续每一步都会被构建问题拖住。

后续决策点：

- Phase 2 完成后，再决定是否切换到 Roslyn syntax。
- Phase 3 再决定是否引入 `MSBuildWorkspace` 和 `Microsoft.Build.Locator`。
- DLL 环境定义只在需要真实工程语义时再引入，不提前绑死。
